# Upgrade to v0.8.0

This guide is suitable for upgrading Kubemox from versions <0.8.0 to v0.8.X.

## Breaking Changes

- `VirtualMachine`, `VirtualMachineSet`, `VirtualMachineTemplate`, `Container`, `StorageDownloadURL` and `CustomCertificate` are now `Namespaced`. `ProxmoxConnection` stays `Cluster` scoped. The scope of a CRD can't be changed in place, so the CRDs have to be recreated and **every object has to be re-created**.
- A validating webhook rejects a `VirtualMachine` whose `spec.name` is already used by another `VirtualMachine` on the same node and `ProxmoxConnection` (in any namespace), or which matches more than one VM on that Proxmox node. The same name on different nodes is allowed. Its serving certificate comes from [cert-manager](https://cert-manager.io/docs/installation/) when cert-manager is installed; otherwise the operator issues a self-signed one, stores it in the `<release>-webhook-cert` Secret and injects the CA into the webhook configuration. Force either with `--set webhook.certManager=true|false`. You can disable the webhook with `--set webhook.enabled=false`, but then nothing stops two namespaces from managing the same VM.
- `CustomCertificate` now creates its cert-manager `Certificate` and reads the TLS Secret in its own namespace, not in the operator's namespace.

!!! danger
    Deleting a `VirtualMachine`, `Container` or `VirtualMachineTemplate` while the operator runs deletes the machine on Proxmox. Keep the operator scaled down and remove the finalizers before you delete anything.

## Upgrade Steps

* Stop the operator.

```shell
kubectl scale deployment kubemox --replicas=0
```

* Back up the resources.

```shell
for kind in virtualmachines virtualmachinesets virtualmachinetemplates containers storagedownloadurls customcertificates; do
  kubectl get "$kind.proxmox.alperen.cloud" -o yaml > "backup-$kind.yaml"
done
```

* Remove the finalizers so that deleting the CRDs doesn't touch Proxmox, then delete the CRDs.

```shell
for kind in virtualmachines virtualmachinesets virtualmachinetemplates containers storagedownloadurls customcertificates; do
  kubectl get "$kind.proxmox.alperen.cloud" -o name | \
    xargs -r -I{} kubectl patch {} --type=merge -p '{"metadata":{"finalizers":null}}'
  kubectl delete crd "$kind.proxmox.alperen.cloud"
done
```

* Upgrade the chart. It installs the new CRDs.

```shell
helm upgrade kubemox alperencelik/kubemox
```

* Restore the resources into a namespace. Strip the server-set fields and skip objects owned by another Kubemox object: a `VirtualMachineSet` re-creates its `VirtualMachine`s and a `VirtualMachineTemplate` re-creates its `StorageDownloadURL`, and both adopt the existing machines on Proxmox by name.

```shell
NAMESPACE=default
for f in backup-*.yaml; do
  yq '.items[] | select(.metadata.ownerReferences == null)
      | del(.metadata.uid, .metadata.resourceVersion, .metadata.creationTimestamp,
            .metadata.generation, .metadata.managedFields, .metadata.finalizers, .status)
      | split_doc' "$f" | kubectl apply -n "$NAMESPACE" -f -
done
```

* Start the operator.

```shell
kubectl scale deployment kubemox --replicas=1
```

* Verify that the resources are in the desired state. `VirtualMachineSnapshot`s now look up their `VirtualMachine` in their own namespace, so keep each snapshot in the same namespace as its VM.
